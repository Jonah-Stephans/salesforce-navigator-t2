# Research: "No such column" on a field created in the same deploy as the test that queries it

**Note on location:** this repo has no `docs/` directory and no established research-notes convention. This file was placed at `docs/research/` as a reasonable new home for one-off primary-source investigations like this one. If a different convention emerges later, this file should move with it.

**Date:** 2026-08-25
**Symptom investigated:** `sf project deploy start --test-level RunLocalTests --wait 60` against a brand-new scratch org, deploying `Navigator_Layout__c` (object + 4 new fields), 2 Apex classes, 6 LWC bundles, 1 CustomTab, 1 PermissionSet in one payload. All 15 non-test components report `componentSuccesses: true`, but 26/40 Apex tests fail with `System.QueryException: No such column 'Is_Active__c'/'Layout_JSON__c'/'Schema_Version__c' on entity 'Navigator_Layout__c'` — never `Sort_Order__c`, `Name`, `OwnerId`, or `Id`. `RunLocalTests` atomicity then rolls back the entire deploy, so nothing lands despite the per-component `success: true` markers.

Already ruled out by the requester before this research started (not re-litigated here): FLS/permissions (plain SOQL, no `WITH SECURITY_ENFORCED`/`WITH USER_MODE`, and the permission set grants edit on all 4 fields anyway); flakiness (byte-identical failures across two fresh scratch orgs and under `--dry-run`); a security-logic bug in the Apex (the two `runAs` cross-user tests pass every time).

## Update, 2026-08-25 (same day): the recommended fix was tested and failed — and the cause is not what either of us thought

The two-step fix below was tried directly against a fresh scratch org: Deploy 1 (`NoTestRun`, full payload) succeeded clean, confirmed the object queryable immediately after. Then, since a second metadata deploy was a no-op (source tracking saw no delta since Deploy 1), ran the tests directly via `sf apex run test --test-level RunLocalTests`. **Identical result: 26/41 failing, same fields, same error text.** The fields came from a separate, already-committed prior deploy this time — there was no shared transaction. The fix made no difference, which rules out the "same transaction" framing this whole document was built around.

Chasing that down further overturned the field-count read, too. `Sort_Order__c` was assumed exempt because it never appeared in an error message. Queried alone, in isolation, via plain REST SOQL (`SELECT Sort_Order__c FROM Navigator_Layout__c`): it fails identically. **All four fields are equally broken** — `Sort_Order__c` was never blamed by name only because SOQL reports just the first unrecognized column in a multi-field `SELECT`, and `Sort_Order__c` never happens to be listed first anywhere in this codebase's queries. Pure reporting artifact, not evidence it was fine.

Then checked lower in the stack:

- `sf sobject describe --sobject Navigator_Layout__c` — none of the 4 custom fields appear. Only the 9 standard fields (`Id`, `OwnerId`, `Name`, etc.).
- Tooling API, `SELECT Id FROM CustomField WHERE TableEnumOrId = 'Navigator_Layout__c'` — zero rows.
- Tooling API, `SELECT Id, DeveloperName FROM CustomField WHERE Id = '<the field's own reported Id>'` — **succeeds**, returns the record.
- `sf project retrieve start --metadata "CustomField:Navigator_Layout__c.Is_Active__c"` — **succeeds**, pulls back a correct, complete field definition.
- Re-ran the plain SOQL query again ~10 minutes and several intervening operations later (a full test run, multiple queries, a Tooling query, a retrieve): still fails. No sign of resolving with elapsed time.

So the field genuinely exists, confirmed two independent ways (a Tooling API record by its own Id, and a full Metadata API retrieve), but is invisible to schema describe, the SOQL query engine, and a Tooling API query filtered by object — for all four fields, not three — and this held for an extended period across many separate operations, not a narrow window right after creation.

**This is not the same-transaction visibility race the rest of this document describes.** That hypothesis predicted the gap would close once field creation and test execution were pulled into separate, sequential deploys. It didn't. Treat the "Bottom line" and "Recommended fix" sections below as **superseded**: they document a reasonable hypothesis that turned out to be wrong when tested directly, kept here for the record rather than deleted.

## Second update, same day: root cause found and confirmed — API v67's user-mode-by-default change

Not a metadata-propagation bug at all. **This project's `sfdx-project.json` sets `sourceApiVersion: 67.0`.** Salesforce's Summer '26 release (API v67) changed the default execution mode for Apex SOQL/SOSL/DML/Database methods from system mode to user mode, for any code compiled at API 67.0+: _"Database Operations Run in User Mode by Default, Not System Mode"_ ([Salesforce Help release note, release 262](https://help.salesforce.com/s/articleView?language=en_US&id=release-notes.rn_apex_default_user_mode.htm&release=262&type=5)). Under user mode, a field the running user lacks field-level security on is treated by SOQL exactly as if it doesn't exist — the literal `No such column` error this entire investigation has been chasing.

`NavigatorLayoutControllerTest.cls`'s helper queries (`storedLayouts()`, `activeCount()`, `activeName()`, `sectionNameOf()`) declare no explicit access mode, so they silently inherited this new default. The org's default/admin user (whichever identity runs the deploy and isn't wrapped in `System.runAs`) is never granted the `Salesforce_Navigator_User` permission set anywhere in the deploy or test setup — only the two `System.runAs` test users get it, inside `@TestSetup`. So the admin has no FLS on any of the four custom fields, and every plain query touching them fails.

**Confirmed directly, not just theorized:** fresh scratch org, deployed with `NoTestRun`, then `sf org assign permset --name Salesforce_Navigator_User` against the org's default admin (the identity actually running the tests), then `sf apex run test --test-level RunLocalTests`. Result: **41 of 41 passing, 100%.**

This explains every piece of evidence gathered above, cleanly:

- **All four fields equally broken** — the admin has FLS on none of them, not on three.
- **Splitting the deploy made no difference** — nothing to do with timing; it's a permissions gap, not a propagation delay.
- **The two `System.runAs` security tests always passed** — those specific methods run as users the test setup explicitly assigns the permission set to.
- **Tooling API by-Id lookup and Metadata API retrieve succeeded while SOQL/describe failed** — those are metadata-layer operations, not gated by the same per-record-field FLS check that now governs plain SOQL by default at API 67.
- **It never surfaced during hand-built development** — very likely because the engineer's own persistent scratch org (`sfnav`/`sfnav-t2`) got the permission set assigned to its admin at some point during manual UI testing (this investigation did exactly that, once, for an unrelated reason — checking the CustomTab's icon — and it silently fixed the org going forward). A fresh org, every time, never has that assignment done first.

**The real fix, going forward:** the test class's verification helpers exist to check the true state of the data regardless of who's running the test — that's what they're for. Under the old system-mode default they did that automatically; under the new one they need to say so explicitly. Salesforce's own migration guidance recommends exactly this: declare an access mode rather than relying on the default. Add `WITH SYSTEM_MODE` to `storedLayouts()`, `activeCount()`, `activeName()`, and `sectionNameOf()` in `NavigatorLayoutControllerTest.cls`. That's a source-code fix, not a CI/deploy-process workaround — no two-step deploy, no pre-assigning permission sets to admin identities required. Not yet applied to the repo; this document records the finding, not the fix.

Everything below this point (all three now-superseded framings: same-transaction race, and the two-step split) is kept for the record, not because any of it turned out correct.

## Bottom line (superseded — see Update above)

**No source found — still a hypothesis.** I could not find any official Salesforce documentation, Known Issues portal entry, `forcedotcom` GitHub issue, Trailblazer Community thread, or Salesforce Stack Exchange post that describes this _exact_ mechanism: fields created in the same deploy transaction as Apex tests that query them, in a brand-new org, producing deterministic (not flaky) `QueryException: No such column` failures that disappear on rollback. The working hypothesis — a brief window where newly-created fields exist for schema/DDL purposes but haven't yet propagated to whatever cache the SOQL query engine consults at runtime — is plausible and consistent with the general shape of known Salesforce metadata-propagation issues, but it is not confirmed by any primary source. Separately, official docs and the general CI/CD deploy-ordering guidance do support a concrete, low-risk fix: split the single deploy into two API calls so field creation and test execution never share a transaction. Confidence on the fix: **plausible community-consensus / reasoned-from-adjacent-official-facts, not a source-confirmed fix for this exact bug.**

## What's documented / what others have reported

### Official Metadata API docs are silent on the exact question

- [`deploy()` | Metadata API Developer Guide](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_deploy.htm) states that **"Apex tests that run as part of a deployment always run synchronously and serially,"** and that `rollbackOnError` governs all-or-nothing atomicity (`"Indicates whether any failure causes a complete rollback (true) or not (false)... This parameter must be set to true if you're deploying to a production org."`). It does **not** state anything about whether newly-created fields are guaranteed to be visible to the SOQL engine used by those synchronous tests within that same transaction. This silence is itself notable: Salesforce has not made a public commitment either way for this specific case.
- [`Running Tests in a Deployment` | Metadata API Developer Guide](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_deploy_running_tests.htm) and [`Testing Metadata Deployments` | Apex Developer Guide](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_metadata_testing.htm) describe _when_ tests run (which test level, based on deployment content) and how to unit-test `Metadata.Deploy` callbacks in Apex — neither describes the internal ordering/propagation mechanics between schema commit and test execution.
- [Salesforce Developers Blog — "Master Metadata API Deployments with Best Practices" (Oct 2025)](https://developer.salesforce.com/blogs/2025/10/master-metadata-api-deployments-with-best-practices) is the one official(-ish) source that states deploy **ordering** explicitly: _"Custom objects must deploy before their custom fields, and Apex classes referencing these fields should deploy only after both the object and fields exist in the target environment."_ It also recommends: _"Break down large deployments into small, logical units"_ and to _"deploy declarative changes... separately from deployments of programmatic components, like Apex classes."_ This is general best-practice guidance from a company blog, not an admission of, or fix for, the specific race in this ticket — but it's the closest official statement supporting a split-deploy approach.
- [Salesforce Developers Blog — "Take a Deep Dive into Metadata API Deployments" (Sep 2025)](https://developer.salesforce.com/blogs/2025/09/take-a-deep-dive-into-metadata-api-deployments) describes deployment as staged (CRUD of components, then an Apex-testing stage, then commit) but gives no detail on cache coherency between the two stages.

### A Known Issue exists with the _identical error text_ but a _different, unrelated cause_

- [Salesforce Known Issue W-2943792 — `"No such column <field> on entity 'Account'" error thrown when compiling or deploying Apex classes with different API versions`](https://help.salesforce.com/s/issue?id=a028c00000qPwuhAAC) (Status: Solution Deployed, fixed in Winter '19). I pulled the full issue body via browser rendering (the page is a JS SPA that plain `WebFetch`/`curl` can't render). It reads: _"An error occurs when compiling two or more classes together (either via Compile All Classes or Deployment) if one of the classes references Account entity fields not available in the API version selected by the compiler... 'No such column on entity Account'... The Apex compiler selects the API version specified by the first class it compiles. If the compiler selects an API version in which a compound field is unavailable, any attempt to access a compound field fails."_ Workaround listed: avoid compound fields (e.g. `Name`, `BillingAddress`); reference component fields directly.
  - **This is a same-symptom-text, different-mechanism issue.** It's about the Apex multi-class compiler picking an inconsistent API version and losing visibility into _compound_ standard fields — nothing to do with newly-created custom fields or same-deploy propagation timing. It does _not_ apply to this ticket's `Navigator_Layout__c` custom fields. Ruling this out for completeness since it was the only Known Issue that surfaced with matching error text.

### One real-world report has the same shape, but a mundane cause (not a race)

- [GitHub issue #362, `SFDO-Community/declarative-lookup-rollup-summaries`](https://github.com/SFDO-Community/declarative-lookup-rollup-summaries/issues/362) — 23 test classes failed on deploy via githubsfdeploy, including `System.QueryException`-style `"No such column 'NumberOfLocations__c' on entity 'Account'"`. On the surface this looks like our bug: new-ish fields, test failures, "No such column," during a deploy. But the repo maintainer (Andrew Fawcett, a well-known Salesforce architect) explained the real cause in the thread: _"There are some sample custom fields included on some of the Standard objects in Developer Edition orgs, which will not be present in your Sandbox. Things like Account.NumberOfLocations__c. The tests do leverage these. The solution is to create these fields in your Sandbox and Production."_ I.e., the fields genuinely didn't exist in the target org at all (DE-org-only sample fields), not a timing/propagation issue. Useful only as confirmation that "field doesn't exist from the query engine's point of view" is a known failure shape in Salesforce test deploys generally — it does not confirm the same-deploy race hypothesis.

### GitHub issue/PR search across `forcedotcom/cli`, `forcedotcom/source-deploy-retrieve`, `salesforcecli/plugin-deploy-retrieve`

Searched via `gh search issues "No such column" org:forcedotcom` and targeted repo searches. - [`forcedotcom/cli` #1876](https://github.com/forcedotcom/cli/issues/1876) and [#1356](https://github.com/forcedotcom/cli/issues/1356) both surfaced from the "No such column" search but resolved to unrelated causes (field-level security not set on retrieve; a malformed ad-hoc SOQL query) — not the deploy-test race.

### NoTestRun eligibility (needed for the recommended fix)

- [`sf project deploy start` | Salesforce CLI Command Reference](https://developer.salesforce.com/docs/platform/salesforce-cli-reference/guide/cli_reference_project_deploy_start.html) confirms `--test-level NoTestRun`: _"No tests are run. This test level applies only to deployments to development environments, such as sandbox, Developer Edition, or trial orgs."_ A scratch org qualifies as a development environment, so `NoTestRun` is legal there (it is rejected in production, consistent with the `INVALID_OPERATION: testLevel of NoTestRun cannot be used in production organizations` error referenced in `forcedotcom/devops-center-feedback`'s [`KNOWNISSUES.md`](https://github.com/forcedotcom/devops-center-feedback/blob/main/KNOWNISSUES.md)).

## Recommended fix (superseded — tested directly, did not work; see Update above)

**Split the single deploy into two sequential `sf project deploy start` calls, gated on the first one's completion:**

1. **Deploy 1** — the exact same payload (object, 4 fields, both Apex classes, 6 LWC bundles, CustomTab, PermissionSet) with `--test-level NoTestRun`. This is legal in a scratch org per the CLI reference above. Everything commits, including the Apex classes and the fields, with zero test execution touching the new fields in this transaction.
2. **Deploy 2** (or `sf apex run test`) — once Deploy 1 reports success, run the tests against the now-already-existing schema, e.g. `sf project deploy start --test-level RunLocalTests` re-submitting the same payload (a no-op metadata-wise, since it already matches the org), or more directly `sf apex run test --test-level RunLocalTests --wait 60` since no metadata changes are pending. Either way, by the time the tests run, the fields were created in a _prior, already-committed_ transaction — which is exactly the condition the working hypothesis says never triggers the failure (this matches how the original hand-built component behaved: fields had existed for a while before the querying tests ran).

**Confidence: plausible / reasoned, not source-confirmed.** No source in this research states "this two-step pattern fixes a same-deploy field-visibility race." The confidence here comes from: (a) `NoTestRun` being officially documented as legal in scratch orgs, (b) Salesforce's own deploy-ordering guidance treating field-then-Apex ordering as significant enough to call out, and (c) the two-step pattern being a straightforward logical negation of the suspected race window (fields are never queried by a test in the same transaction that created them) regardless of whatever the _actual_ internal cache/propagation mechanism turns out to be. It is not a workaround anyone else has published for this precise bug, because I couldn't find anyone else who has published this precise bug.

**No single-deploy fix or documented retry/wait/delay pattern was found.** Neither the Metadata API `deploy()` reference nor the `sf project deploy start` CLI reference expose any parameter for "settle time" or "propagation delay" before tests start; `--wait` only controls how long the CLI polls for the deploy job to finish, not any pre-test delay. If a same-deploy fix exists (e.g., an internal ordering hint, a manifest-ordering trick, or deploying fields as a preceding "batch" within one zip), no source I found documents it. The two-step deploy is the only fix pattern this research turned up, and it's a workaround inferred from adjacent facts, not a documented fix for the specific bug.

**Conflict with "single payload" deployment goal:** this recommendation directly conflicts with deploying the whole spec as one atomic payload. If atomicity of "the whole feature lands or nothing does" matters (e.g., for change-set-style review, or because Deploy 1 landing without Deploy 2 succeeding would leave inert, untested code in the org), that property is given up by splitting the deploy. Practical mitigations if that matters: script both `sf project deploy start` calls back-to-back in the same CI job so they're inseparable in practice even though they're two API calls; or treat Deploy 1 (`NoTestRun`) as effectively a dry-run/validation-adjacent step and only consider the feature "shipped" once Deploy 2 (`RunLocalTests`) also succeeds, failing the pipeline (and optionally rolling back Deploy 1's artifacts manually) if it doesn't.
