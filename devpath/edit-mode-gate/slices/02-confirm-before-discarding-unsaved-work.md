# Unsaved work is not thrown away without asking

> Watch a new test go red before you make it green.
> _Why: a test written before the code cannot be written to hit a coverage number — there is nothing to
> cover yet. Retires when Apex gets mutation testing._

## What to build

A user who cancels edit mode, or switches to a different saved layout while editing, is asked to confirm
first whenever there is unsaved work to lose — and is not asked when there is nothing to lose.

## Acceptance criteria

- [x] met Cancel on an edit session in which nothing was changed closes edit mode without asking anything. Proved by `closes edit mode without asking when Cancel is pressed on an untouched session` (`salesforceNavigator.test.js`, `entering and leaving edit mode`). Guard: `handleEditCancel`'s `if (this.hasUnsavedCanvasChanges)`, forced to `if (true)` — reddened (the prompt appeared where it should not have); restored, green.
- [x] met Cancel on an edit session with unsaved canvas changes asks the user to confirm before discarding. Proved by `asks before discarding when Cancel is pressed with unsaved canvas changes, and declining leaves the user editing with them intact`. Same guard, forced to `if (false)` — reddened (no `[role="alertdialog"]` appeared); restored, green.
- [x] met Confirming discards the changes and leaves edit mode; declining leaves the user in edit mode with the changes still on screen. Confirming proved by `confirming the discard prompt on Cancel throws the unsaved changes away and leaves edit mode` — guard: `handleDiscardConfirm`'s `action.type === DISCARD_CANCEL` branch, forced to `if (false)` — reddened (the section added before Cancel survived); restored, green. Declining proved by the same test as the criterion above, which presses "Keep editing" and asserts the change and the Save button are both still there.
- [x] met Selecting a different saved layout while editing with unsaved changes asks the same question, by the same route. Proved by `asks before discarding when switching layouts while editing with unsaved changes, and declining stays on the layout being edited` and `confirming the discard prompt on a layout switch throws the draft away and switches, by the same route Cancel uses` (`switching between layouts` describe). Guard: the Tier 3 branch's `if (this.isEditing && this.hasUnsavedCanvasChanges)`, forced both `false` (reddened: no dialog, immediate switch) and `true` (reddened: `switches immediately, without asking, when editing with nothing unsaved` broke); restored, green both times. Widened to New layout and Delete layout too — see `## Deviations`.
- [x] met Whether there is anything to lose is decided by comparing the serialised current layout against the serialised snapshot taken on entry, so the question is asked exactly when a write would differ. This is `hasUnsavedCanvasChanges`, unchanged from slice 01 and reused rather than reimplemented: `serializeLayout(this.layout) !== this.editSnapshot.json`. Proved by `closes without asking when a change is undone back to exactly its entry value` (columns set to 6 then back to 2, Cancel closes silently) — mutating the getter to `return true;` (a stand-in for a dirty-flag protocol that never un-sets on an exact revert) reddened that test *and* `closes edit mode without asking when Cancel is pressed on an untouched session` *and* `switches immediately, without asking, when editing with nothing unsaved`; restored, all green.
- [x] met The confirmation reuses the component's existing inline prompt rather than adding a third dialog mechanism beside the prompt and the item picker's modal. `PROMPT_DISCARD` is one more value of the same `layoutPrompt` field `PROMPT_NEW`/`PROMPT_RENAME`/`PROMPT_DELETE` already use, opened via the existing `openPrompt`/closed via the existing `closePrompt`, rendered in the same `lwc:if`/`lwc:elseif` chain inside the same `.rstk-nav-layout-prompt` container `PROMPT_DELETE` already renders in (input-less, `role="alertdialog"`, borrowed verbatim). No `LightningConfirm` or any other dialog import exists anywhere in `salesforceNavigator.js` — verified by grep, checked as part of this pass.

## Deviations

- **Widened from two call sites to four, per the orchestrator's instruction.** The design's own text and this slice's original criteria name only Cancel and switching layouts. Slice 01's critique left an open box (`- [ ] Creating a new layout, or deleting one, inside an edit session discards the unsaved Tier 1 draft without asking...`) naming New layout and Delete layout as a third and fourth call site for the identical hazard — each replaces the canvas wholesale (`createNewLayout` via `buildSeededLayout`, `deleteCurrentLayout` via `adoptFromStore`) and re-takes the entry snapshot (`resnapshotEdit`), so an unsaved Tier 1 draft is simply gone with nothing left to Cancel back to. Built the whole set: `handleLayoutNameCommit`'s `PROMPT_NEW` branch and `handleLayoutDeleteConfirm` both now check `hasUnsavedCanvasChanges` and open the same shared prompt before proceeding. One path (`openDiscardPrompt`/`handleDiscardConfirm`/`PROMPT_DISCARD`), four call sites (`DISCARD_CANCEL`, `DISCARD_SWITCH`, and `NEW_LAYOUT`/`DELETE_LAYOUT` reused as the action tag rather than a second pair of near-identical constants).
- **`pendingDiscardAction` is a small tagged object (`{ type, ... }`), not four booleans or four prompt values.** One field, matching the shape `layoutPrompt` itself already uses ("one field rather than four booleans so two cannot be open at once") and `creatingLayout`'s own precedent for carrying identity (`{ promise, distinct }`) rather than adding a parallel field per call site. `DISCARD_SWITCH` carries `layoutId`; `NEW_LAYOUT` carries the `name` the user had already typed in the naming prompt before the discard prompt intervened, so confirming does not lose it.
- **The four call sites check `hasUnsavedCanvasChanges` at their own handler, not inside a shared entry-point wrapper.** A 2-3 line `if (hasUnsavedCanvasChanges) { openDiscardPrompt(...); return; }` is repeated at `handleEditCancel`, the Tier 3 branch of `handleLayoutMenuSelect`, `handleLayoutNameCommit`, and `handleLayoutDeleteConfirm`. This mirrors the codebase's own established pattern for "one thing done at each of the four writing entry points" (`beginWrite()`/`endWrite()`, called the same way at the same four kinds of site) rather than a DRY violation — the actual shared logic (`openDiscardPrompt`, `handleDiscardConfirm`, the prompt markup) lives in exactly one place each.
- **One shared message (`DISCARD_PROMPT_MESSAGE`), not four call-site-specific sentences.** `layoutDeleteMessage` names the layout being deleted because that is the one detail a bare "Delete?" would leave out; the discard prompt does not need call-site-specific wording to be equally informative, because each call site's own control (Cancel, the layout switcher, New layout, Delete layout) already says what happens once the draft is gone. Kept the surface small rather than branching on `pendingDiscardAction.type` for a sentence, per `rstk-complexity-guard.md`.
- **The picker fix (inherited item 2): `addChosenItem` refuses when the session has changed, not "closes the picker" on leaving edit mode.** Two shapes were on the table. Closing the already-open `NavigatorItemPicker` from `leaveEditMode()` — the `closePrompt()` precedent the design itself points to — is not reachable the same way: `lightning/modal`'s `.open()` returns only a promise, never a component handle the caller could call `.close()` on, so making the parent close it would mean giving `NavigatorItemPicker` a new externally-triggered close path — a change to `navigatorItemPicker.js`, which is outside this slice's `touches:` list, or a `document.querySelector` reach across the shadow boundary, which `rstk-lwc-standards.md` forbids outright. Refusing on resolution needs no new surface anywhere: `addChosenItem` already gates on `isAttached`, and the fix adds one more comparison in the same place. **The guard is a session-identity check (`this.editSnapshot !== session`, captured at the moment `handleSectionAddItems` opens the picker), not a bare `!this.isEditing` return** — a bare mode check has a gap the session check closes and the other shape (closing the picker) would not have needed to think about at all: Cancel ends a session, but re-entering edit mode starts a *new* one with a *new* `editSnapshot` object while `isEditing` reads `true` throughout, so a bare mode check would let a stale, already-discarded choice land on a session the user never made it in. Mutation-confirmed the gap is real: keeping `!this.isEditing` alone and dropping only the session comparison leaves `does not write when a chosen item resolves after Cancel has ended the session that opened the picker` green but reddens `does not let a stale picker's choice land on a different, later edit session` — the exact shape the finding warned a bare check would miss.
- **`closePrompt()` now also clears `pendingDiscardAction`,** on the same reasoning it already clears `draftLayoutName`: transient dialog state that must not outlive the dialog, whether the dialog closes by "Keep editing", by Escape (`handleLayoutPromptKeydown`), or by `leaveEditMode()`'s own unconditional `closePrompt()` call.
