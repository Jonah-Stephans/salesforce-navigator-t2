# Out of edit mode nothing can be dragged or grabbed

> Watch a new test go red before you make it green.
> _Why: a test written before the code cannot be written to hit a coverage number — there is nothing to
> cover yet. Retires when Apex gets mutation testing._

## What to build

Out of edit mode a user cannot rearrange the Navigator by any route — sections and items are not
draggable by pointer and cannot be grabbed from the keyboard — while clicking a link goes on working
exactly as it does today.

## Acceptance criteria

- [x] met Out of edit mode a section card and an item anchor both report `draggable="false"`.
- [x] met Out of edit mode pressing Space on a section or an item does not grab it, and no announcement is made.
- [x] met Out of edit mode a section card is not a tab stop, so a keyboard user moving through the panel stops only on links.
- [x] met In edit mode pointer dragging and the full keyboard grab-move-drop-cancel path both work exactly as they do today, announcements included.
- [x] met Clicking a link out of edit mode navigates, and a Ctrl-, Cmd- or Shift-click still reaches the browser instead of being intercepted.
- [x] met Leaving edit mode clears any keyboard grab that was in flight, so focus restoration cannot chase a card that is no longer grabbable.
- [x] met The comment in `navigatorItem.css` asserting that there is no edit mode is replaced with one recording what superseded it, not deleted.

## Critique findings

- [ ] real — `salesforceNavigator.test.js:1989` "writes nothing when a section card is dropped back on itself" is vacuous. Delete the guard it names by name — `if (from === to) { return; }` in `handleSectionDrop` (`salesforceNavigator.js:1593-1595`) — and all 518 tests stay green. Under explicit save a self-drop calls `applyLayout` with a byte-identical canvas, `scheduleSave` returns early while editing, and Save's `hasUnsavedCanvasChanges` finds no change, so "writes nothing" is satisfied by the no-op-save guard rather than by the short-circuit. This is a coverage regression introduced by this slice, not a pre-existing one: the same mutation run against the parent commit `8ea706d` reddens that test, because there `navigatorWithSections` mounted out of edit mode and `settleAutosave` still armed the debounce on the redundant `applyLayout`. The `## Deviations` bullet claims this rewrite put the assertion "back to discriminating the guard it names"; it did not. Note for whoever fixes it: swapping `settleAutosave` for `saveEdits` + `not.toHaveBeenCalled()` — trap 273's own prescribed retarget — is not sufficient for the no-op-guard subclass, because `hasUnsavedCanvasChanges` swallows the mutation exactly as `isEditing` did. A discriminating assertion here has to be non-Apex (that `applyLayout` never ran), or has to drive the gesture through a vehicle that is still outside edit mode. The three sibling rewrites were checked the same way and all three redden: `:1663` item Escape, `:1888` section Escape, `:1956` abandoned section drag.
- [ ] real — `draggable={editing}` fails **open**, not closed, when `editing` is `undefined`. Probed in this environment: with `editing` explicitly bound to `undefined`, LWC removes the attribute outright (`hasAttribute` false, `getAttribute` null) and `anchor.draggable` then reads `true`, because an `<a href>` is natively draggable and only an explicit `"false"` overrides that. Both `editing` setters store the incoming value uncoerced (`navigatorItem.js:115-120`, `navigatorSection.js:143-161`) on a public `@api` boundary. Not reachable through today's wiring — `isEditing`, `isEditingSection` and `isEditingItem` are all boolean-initialised class fields — and both "out of edit mode" tests exercise the class-field default rather than a passed `undefined`, so nothing here pins the difference. One-line fix on each setter (`value === true`) if it is judged worth closing.
- [ ] real — criterion 2's second clause, "no announcement is made", is asserted on the section axis only. The composed section test asserts the live region is empty (`salesforceNavigator.test.js:1807-1809`); its item counterpart at `:1536` asserts only the `grabbed` flags and the absence of a write. Removing the item gate reddens exactly two tests (`navigatorItem` "does not grab on Space out of edit mode" and the composed `:1536`), neither of which would catch a gate that suppressed the grab and still announced. Structurally the announcement cannot fire — it lives in `navigatorSection.handleItemGrab`, downstream of the `itemgrab` the gate withholds — so this is a coverage asymmetry rather than a live defect, but the criterion was ticked on both axes.
- [ ] real — out of edit mode a section card still behaves as a drop target for a foreign drag. `handleCardDragOver` (`navigatorSection.js:827-833`) calls `preventDefault()` and sets `dropEffect = "move"` unconditionally, so dragging a file, a link or a text selection over a card shows a move cursor and suppresses the browser's own default.
