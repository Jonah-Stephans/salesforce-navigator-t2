Section widths — a geometry sketch

Every width on this page is computed from the real formula and the real SLDS spacing tokens (spacing-2: 0.5rem, spacing-4: 1rem). Change the per-column unit and the viewport and watch whether a row fits or scrolls. The question this answers is proportion: is a row of narrow sections the right shape, and is the column unit wide enough for a tab label.

This is not a Lightning facsimile, deliberately. Density, chrome and native feel are only answerable in a real org — feedback on this page's own inaccuracies would be feedback on the wrong thing. Judge the geometry here; judge the look in a scratch org at Build.

Ellipsis versus wrap, same section, same width

Both cards below are the identical 3-column section at the current unit — same width, to the pixel. Wrapping costs height, never width, so every number elsewhere on this page is unaffected by this choice.

The same long label at every unit

A column track is exactly --rstk-nav-col-width wide whatever the section's column count, so truncation is identical in a 1-column section and a 6-column one — the unit is the only thing that moves it. Character counts are measured, not estimated.

Rows under a column budget of 6

Each row below holds sections whose column counts sum to 6 — the budget from Q2. Row width is 992 + 40k px for k sections at a 10rem unit, so the widest row is always the one with the most sections.

The Small form factor, for comparison

One section per row at full viewport width with minmax(0, 1fr) tracks — today's behaviour, unchanged. Nothing here is at a keyed width, so nothing overflows.

The formula

section(n)  =  n·col  +  (n−1)·8  +  2·16
row(counts) =  Σ section(nᵢ)  +  (k−1)·16
canvas     =  row  +  2·16
